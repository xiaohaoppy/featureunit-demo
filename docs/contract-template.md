# 功能规格模板：FeatureUnit 六要素（v1）

> 用途：给"功能规格设计师"（人或 AI）填写。一份功能规格 = 一个功能单元的全部规格。
> 对应代码：`contract.ts`（可执行部分：zod schema + 接口）+ `spec.md`（语义部分：本文档的落地形态）。

---

## 1. 一句话目标

用一句话说清"这个单元做什么"。写不出一句话 = 拆得不够细，回去重拆。

```
用户提交订单 → 系统校验商品库存并创建订单。本单元不负责支付。
```

## 2. 输入

列出每个输入字段 + 类型 + 边界规则。边界校验写进 zod schema（这是可执行的部分）。

```
{ items: [{ productId: string, quantity: number(1..99) }] }
语义约束：同一商品重复出现 → 合并数量（幂等语义）。
```

## 3. 输出

成功返回什么（结构化）；失败怎么表达（抛 AppError，见第 4 节）。

```
成功 → { orderId: string, total: number }。失败 → 抛 AppError，错误码见第 4 节。
```

## 4. 错误码

每个失败路径一个错误码 + HTTP 状态码。**问自己：每个输入/每个数据接口调用可能失败吗？失败是什么码？**

```
- INVALID_INPUT (400)：items 为空 / 数量越界（zod 兜底，单元可假定已校验）
- STOCK_SHORT (409)：任一商品库存不足（由注入的库存数据接口判定）
- RATE_LIMITED (429)：同一用户 10 分钟内超过 5 单（由注入的限流数据接口判定）
```

## 5. 数据接口（外部世界的唯一切口）

列出本单元依赖的所有数据接口 + 每个接口"为什么需要"。**规则：数据接口里禁止出现 ORM / HTTP / 框架类型；语义必须能被内存适配器完整模拟。**

```
- inventory: InventoryStore      # 查/扣库存
- orders: OrderStore             # 存订单
- rate: RateLimiter              # 限流判定
- now: () => Date                # 时钟注入（测试可固定时间）
```

## 6. 不变量 / 边界情况（AI 必须满足的硬约束）

至少 3 条，**每条都必须可被测试断言**（写不出来测试的"不变量"是伪要求）。用【不】开头显式声明非目标。

```
- 库存不足 → 不扣任何库存、不创建订单、返回 STOCK_SHORT（失败原子性）
- 重复提交（同一幂等键）→ 返回同一订单，不重复扣库存
- 订单总价 = 各商品单价 × 数量之和，金额用整数分计算
- 【不】负责：支付、物流、优惠券分摊
```

---

## 填写纪律（给功能规格设计师）

1. **只写规格，不写实现**——功能规格里出现"用 X 框架/库"字样 = 越界，删掉；
2. 每个数据接口都要问："接口背后的实现细节，单元需要知道吗？"——不需要就抽象掉；
3. 每个输入都要问："这值非法会怎样？"——必须给出错误码；
4. 不变量必须 ≥ 3 条且条条可测；
5. 语义用中文，签名用 TypeScript。
