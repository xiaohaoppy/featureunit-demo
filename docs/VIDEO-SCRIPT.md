# 视频脚本：用 FeatureUnit 框架设计一个"让 AI 放心写代码"的流程

> 用途：记录一次真实的框架设计 + 实战开发全过程，供以后设计做参考。
> 拍摄方式：全程录屏（管理台 + 终端），旁白按"台词"念，字幕按"字幕"打。
> 建议总时长：12–14 分钟。每个分镜的"操作"就是录屏时要做的事。

---

| 项 | 内容 |
|---|---|
| 画面 | 管理台首页（🏠 开始 tab），镜头缓慢推进到输入框 |
| 操作 | 打开 http://localhost:3001/admin |
| 旁白 | 做这个框架的起因很简单：AI 写代码我们不敢确认。不是 AI 写得不好，是"凭什么说它写完了"。所以我想设计一套流程：**AI 生成 → 机器判据 → 人确认**，每一步都有客观证据，人只为自己确认过的东西负责。 |
| 字幕 | 人只说一句话，AI 逐步生成，机器判据把关，人在每一步确认 |
| 小贴士 | 这里可以插入一张手绘概念图：人 → 一句话 → 流水线 → 定稿(git) |

## 第 1 镜 · 设计主线（约 1 分 30 秒）

| 项 | 内容 |
|---|---|
| 画面 | 依次切：功能规格定稿页 → 验收测试页 → 实现页 → 接入页（📦 功能开发 tab） |
| 操作 | 演示一个已接入功能的 5 步进度条 |
| 旁白 | 核心设计是三件事。第一，**功能要小**——AI 一次只写一个函数，上下文小，不容易迷路。第二，**判据要客观**——验收测试 + 类型检查 + 自动检查，机器说了算，不许"感觉对了"。第三，**人要在每个关口**——定稿、补全测试、修实现、确认接入，全部 git 留痕。设计上还有一条铁律：**生成者 ≠ 验收测试者 ≠ 实现者**，考卷不能是考生自己出的。 |
| 字幕 | ① 功能单元 = AI 一次交付的最小单位 ② 机器判据 = 验收测试 + tsc + 自动检查 ③ 人确认 = 定稿进 git，可追溯 |

| 字幕 | 自动规划：业务系统 inventory-service / 数据接口 inventory-snapshot / 功能 record-stock-movement |

## 第 3 镜 · 人补全功能规格（约 1 分 30 秒）

| 项 | 内容 |
|---|---|
| 画面 | 功能规格编辑器（contract.ts），高亮修改处 |
| 操作 | 展示 mock 草稿的缺陷 → 编辑：具体字段（sku/delta/operatorId）→ 加入 kv 存储依赖 → 写 5 条不变量 → 保存（git 留痕提示） |
| 旁白 | AI 生成的草稿永远要当它有洞。这份草稿 payload 是 any、依赖里没有存储、不变量只有一条——我作为人把它补成真正可验收的规格：输入字段具体化，**依赖里加 kv 存储**（这正好验证数据接口和存储的对接），不变量写到 5 条，包括"delta 为 0 必须报错""时间必须来自注入的时钟"。注意：人编辑定稿区文件是允许的，每次保存都 git 留痕。 |
| 字幕 | 人补全：具体字段 + kv 存储依赖 + 5 条不变量（每条都可被测试断言） |

## 第 4 镜 · 验收测试：占位被拦 → 人补全（约 1 分 30 秒）

| 项 | 内容 |
|---|---|
| 画面 | ④ 确认被拒（占位拦截）→ 验收测试编辑器 → 补全断言 → 跑测试 4/4 绿 |
| 操作 | 直接确认 ④（被拦，展示错误）→ 编辑 impl.test.ts 写真实断言 → vitest 通过 |
| 旁白 | 流水线生成的是测试骨架，全是 TODO——直接确认会被拦："验收测试仍是占位"。这是纪律：**考卷没写完不许开考**。我补上真实断言：写入 kv、多次变动追加不覆盖、delta 为 0 抛 INVALID_INPUT、时间戳来自注入时钟。四条全绿。 |
| 字幕 | 占位验收测试禁止定稿——考卷写完才开考；补全真实断言后 4/4 全绿 |

## 第 5 镜 · 实现：AI 停手求援 → 人修复（约 1 分钟）

| 项 | 内容 |
|---|---|
| 画面 | ⑤ 实现确认 → "达到最大迭代 2 轮仍未通过验收测试——停手" → 编辑 impl.ts → 重跑测试绿 |
| 操作 | 确认实现（接受停手）→ 人编辑 impl.ts 写入 kv 存储逻辑 → vitest 绿 |
| 旁白 | mock 实现器迭代了两轮还是红——它选择**停手求援**而不是假装成功。这是失败安全设计：干不了就明说。我作为人来修实现：写入 kv、时间戳用注入的时钟、日志留痕。测试马上全绿。 |
| 字幕 | 失败安全：迭代超限停手求援，绝不假装成功；人修复实现 → 验收测试全绿 |

## 第 6 镜 · 接入：预演失败 → 追根因（约 2 分钟）

| 项 | 内容 |
|---|---|
| 画面 | ⑥ 接入确认 → 编译预检失败 15 处 → 展示 tsc 错误 → 修复路径/now → 重试通过 |
| 操作 | 确认 ⑥（失败）→ 展示预检 detail（tsc 15 错）→ 修复契约路径与 now 依赖 → 再确认 → 编译预检通过 |
| 旁白 | 接入是机器判据最硬的一关：生成接入 → 写入 → tsc → 自动还原，编译不过禁止确认。第一次预演失败：15 处类型错误。看 detail——相对路径写错了一层，还有一个真问题：**时钟注入 now 没写进契约的依赖**，实现用了它编译器就红。修完功能规格和测试，再确认。这里还暴露一个流程缺陷：预演失败后流水线一直用旧草稿，人修了文件也没用——我给它加了**失败自动重试**，重新生成草稿再判。 |
| 字幕 | 编译预检 = 写入 → tsc → 自动还原；失败时自动按最新文件重试（流程缺陷修复） |

## 第 7 镜 · 端到端验证：HTTP + 存储（约 2 分钟）

| 项 | 内容 |
|---|---|
| 画面 | 业务测试面板（inventory-service 组）→ 记录库存变动 → 200；delta=0 → 400；切 file 存储模式 → 再次写入 → 打开 data/kv.json |
| 操作 | 业务测试面板选 inventory-service → 发送入库请求（200）→ 改 delta=0（400 INVALID_INPUT）→ 配置面板 USER_STORE=file → 再写一笔 → 展示 data/kv.json 内容 |
| 旁白 | 功能上线后三个验证。第一，HTTP 冒烟：入库 200，delta 为 0 被组合根 zod 边界拦成 400——机器判据在工作。第二，**存储承载**：把存储模式从 memory 切到 file，数据真实落盘 data/kv.json，键是 stock:SKU:时间戳，值是完整 JSON——数据接口、组合根、存储三层真正打通了。第三，这里是彩蛋：第一次点业务测试面板，发现**我的功能没有出现在面板里**——因为面板操作列表是写死的。我把它改成**动态发现**：接入的功能自动出现，还按业务系统分组。 |
| 字幕 | HTTP 冒烟 200/400 ✓ 存储切换 file → kv.json 落盘 ✓ 面板动态发现操作（缺陷修复） |

## 第 8 镜 · 藏在后面的四个坑（约 2 分 30 秒）

| 项 | 内容 |
|---|---|
| 画面 | 依次展示四处修复的 diff：① http.ts 路由在 return 之后 ② manifest 尾逗号 ③ bizAppFor 缓存指纹 ④ wiring 自动重试 |
| 操作 | 打开 git log / diff 展示修复提交；或切到代码浏览 tab 逐个展示 |
| 旁白 | 这次实战最值钱的不是功能本身，是揪出的四个坑。第一个，**编译通过不等于路由可达**——接入生成的路由被插在 return app 之后，是死代码，tsc 全绿但 HTTP 永远 404，只有真打一次请求才暴露。第二个，**文本拼接 JSON 必翻车**——manifest 登记功能用字符串插入，产生尾逗号，tsc 不查 JSON，直到面板读它才炸，改成结构化更新。第三个，**缓存要盯文件变更**——试玩实例只按配置版本重建，接入新功能后还在用旧实例，指纹加上组合根和 http 的 mtime 才解决。第四个，**失败要能重试**——预演失败后流水线卡死在旧结果，人修了文件也白搭，加了自动重试。 |
| 字幕 | ① 死代码路由（编译绿 HTTP 404）② manifest JSON 尾逗号 ③ 实例缓存不看文件变更 ④ 预演失败无法重试 —— 全部沉淀为 smoke 防回归检查 |

## 第 10 镜 · 边界与收尾（约 1 分钟）

| 项 | 内容 |
|---|---|
| 画面 | 文档「适合开发什么/不适合开发什么」章节 + 框架主界面定格 |
| 操作 | 打开 README 或指南的适用边界表格 |
| 旁白 | 最后是设计复盘最重要的一句话：这个框架**适合开发"可被考试的功能"**——业务服务、数据接口这类边界清晰、能写客观验收测试的东西；**不适合**探索性原型、强耦合横切改造、UI 界面这类"完成"无法机器判定的东西。判断标准就一条：**"完成"能否被机器判定？** 能，就让 AI 放心写；不能，先别让 AI 写。人负责业务风险，机器负责是否完成，AI 负责怎么写——这就是我想要的"让 AI 放心写代码"。 |
| 字幕 | 适合：业务服务/数据接口（完成可机器判定） 不适合：探索原型/横切改造/UI（无法机器判定） 判断标准："完成"能否被机器判定 |
| 小贴士 | 结尾放一张总结卡：AI 生成 → 机器判据 → 人确认，git 留痕，人人可追溯 |
