# FeatureUnit 框架完整指南

> **术语对照（人话 → 框架术语）**：
> 功能 = 功能单元 ｜ 数据接口 = 端口 ｜ 业务系统 = 服务组 ｜ 功能规格 = 契约
> 验收测试 = 判据 ｜ 定稿 = 冻结 ｜ 接入 = 接线/打包 ｜ 自动检查 = 机器初审
> 编译预检 = tsc 预演 ｜ 总装文件 = 组合根 ｜ AI 助手 = Agent ｜ 任务单 = Ticket

> **让 AI 放心写代码的框架**。核心公式：
> **AI 生成 → 机器验收测试 → 人确认**，每个产物定稿进 git。
> 本指南讲"为什么"，操作见 `USAGE.md`，实操见 `TUTORIAL.md`。

## 1. 缘起

AI 写代码有三个天然问题，框架逐一解决：

| 问题 | 表现 | 解法 |
|---|---|---|
| 验收测试不客观 | AI"感觉写得对"，没人敢确认 | 验收测试 = 测试全绿 + 类型检查 + 初审清单，机器判定 |
| 上下文太大 | AI 面对整个代码库容易迷路 | 一次只给 2 个文件（功能规格 + 实现），其余只读 |
| 人无法负责 | 出问题不知谁的锅 | 功能规格定稿 + 角色分离 + git 全程留痕，每个决策可追溯 |

## 2. 核心思想

```
人一句话需求 → 系统自动规划（组/数据接口/功能）
  → 逐步 AI 生成（六 AI 助手 各司其职）
  → 机器验收测试把关（初审/红灯考卷/编译预检）
  → 人确认 → 定稿（git 提交）
```

**自由与纪律的分界**：功能内自由（AI 怎么写都行），功能间纪律（功能规格/验收测试/数据接口/组合根定稿）。
自由的代价由验收测试承担，纪律的代价由流程承担。

## 3. 概念分层

| 层次 | 是什么 | 解决什么问题 |
|---|---|---|
| 功能 | AI 一次交付的最小单位：contract/spec/impl/test 4 文件 | 上下文极小、验收测试客观 |
| 数据接口 Port | 功能与外部世界的唯一切口（纯接口，无实现） | AI 不需要懂 DB/HTTP/日志 |
| 实现 Adapter | 数据接口的具体实现（内存/scrypt/sqlite/文件/HTTP） | 换基础设施 = 换一行配置 |
| 业务系统 | 一个可部署进程（一个库一个组） | 部署功能，不是微服务 |
| 组合根 | 唯一"知道一切"的文件（index.ts） | 组合逻辑只有一处 |
| manifest | 组清单（版本、规则） | 独立版本、单功能回滚 |

关键区分：**功能是开发功能（进程内、可独立测试），业务系统是部署功能（一个进程）**。

## 4. 五个机制

1. **验收测试客观**：测试全绿 + tsc 通过 = 完成，机器判定；
2. **上下文极小**：ticket 只涉及 2 个文件；
3. **失败隔离**：功能独立测试、独立版本（manifest），回滚粒度 = 单功能；
4. **功能规格定稿**：功能规格/验收测试/数据接口 hash 进 CI，AI 改了验收测试 = CI 红；定稿守卫（已定稿禁止 AI 覆盖）；
5. **角色分离（test oracle 独立性）**：生成者 ≠ 验收测试者 ≠ 实现者——B 的验收测试不是 C 写的，C 必须硬过 B 的考卷。

## 5. 功能规格体系

### 5.1 六要素模板（`docs/contract-template.md`）

一句话目标 / 输入 / 输出 / 错误编号 / 数据接口 / 不变量。

- **不变量 ≥ 3 条，编号列表书写（1. 2. 3.），条条可被测试断言**（自动检查按编号统计）；
- 用**【不】负责**显式声明非目标；
- 语义中文、签名 TypeScript（zod schema = 可执行规格）。

### 5.2 评审清单（`docs/contract-review-checklist.md`）

10 条，定稿前必过：安全边界 / 错误编号齐全 / 数据接口无泄漏 / 不变量可测 / 【不】负责声明 / schema 够严 / 不写死实现 / 时钟可注入 / 日志禁敏感 / 结果不含敏感。
**AI 负责翻译需求，人负责钉业务风险**（防枚举、防重放、防爆破）。

### 5.3 定稿 = git + 守卫

评审通过 → 文件头写定稿记录（评审人/日期/结果）→ git 提交 → 定稿守卫生效：
已定稿的功能规格/验收测试/数据接口禁止被 AI 生成覆盖（lib + 前端双重拦截）。

### 5.4 功能规格演进（唯一允许改功能规格的通道）

1. 新开 v2 功能规格（旧实现继续跑）；
2. 写迁移测试（v1 数据在 v2 下仍可用，或声明破坏性）；
3. 所有调用方一起升级（人评审）；
4. 删除旧版。整个过程不进 AI 队列。

## 6. 错误处理协议

```
功能只抛 AppError(错误编号, 状态码)      ← 业务语义
HTTP 实现：错误编号 → 状态码 + 用户文案   ← 展示层
未知错误：实现兜底 500 + 服务端日志     ← 不泄漏堆栈
```

- 错误编号常量在 `ports/errors.ts`，可 grep、可断言、可枚举；
- 安全相关码有讲究：`INVALID_CREDENTIALS` 同时覆盖"用户不存在"和"密码错误"（防枚举）；
- **错误编号一致性检查**（管理台）：spec 声明 vs impl 抛出 vs errors.ts 定义三方核对；
  `INVALID_INPUT` 由组合根 zod 边界兜底，不算功能漏抛。

## 7. 配置与安全

- 优先级：**本地配置文件（`.featureunit.local.json`，git 忽略）→ 环境变量 → 代码默认值**；
- `config.ts` 是唯一读配置的文件（fail fast：缺失即退出）；
- 秘密（AI 密钥等）默认打码，不进功能、不进测试、不进日志；
- **AI 配置**：`AI_API_KEY` / `AI_MODEL`（自动从 /models 获取，60s 缓存）/ `AI_REASONING`（low/medium/high）/ `AI_BASE_URL`；
- TTL、限流参数由组合根从配置换算后注入功能。

## 8. 机器验收测试体系（框架的"考试系统"）

| 环节 | 机器验收测试 | 语义 |
|---|---|---|
| 数据接口 | 7 项纪律初审 | 机器查纪律，人查语义 |
| 功能规格 | 结构/数据接口引用/tsc 初审 | 考卷质量把关 |
| 验收测试 | 占位检测（TODO/expect(true) 拒绝定稿） | 考卷没写完不许开考 |
| 实现 | 验收测试全绿才提交；迭代 ≤5 轮超限停手 | 失败安全：干不了就求援 |
| 接入 | **编译预检**（写入→编译→自动还原，零污染） | 编译不过禁止确认 |
| 全局 | 定稿守卫 + 错误编号一致性 + 接入检查（6 项缺口） | 多层防线 |

**初审检查器本身也接受"真实 AI 生成测试"校准**——mock 的固定缺陷喂不出的假阴性（JSDoc 多行注释、不变量计数），真实产物一测就暴露。

## 9. 六 AI 助手 全景

| AI 助手 | Prompt | 产出 | 机器验收测试 | 自动开发推理等级 |
|---|---|---|---|---|
| 需求解析 | `analyzeRequirement` | 组/功能/数据接口方案 | — | — |
| A 功能规格设计师 | `01` | contract.ts + spec.md | 结构/数据接口/tsc 初审 | **high** |
| B 评审员/验收测试作者 | `02` + `04` | 评审结论 / impl.test.ts | 占位检测 | **high** |
| C 功能实现者 | `03` | impl.ts | 验收测试全绿才提交 | medium |
| D 数据接口作者 | `05` | ports/<name>.ts | 7 项纪律初审 | medium |
| E 接入作者 | `06` | 组合根/HTTP/manifest 接入 | 编译预检 | medium |

**Prompt 质量基线**（已统一）：`{{占位符}}` 风格、输出格式约束（只输出代码块）、
纪律白名单化（禁止 import 什么明确列出）、few-shot 好/坏示例（05）、编号格式约束（01）。

## 10. 数据层与存储

| 存储 | 用途 | 说明 |
|---|---|---|
| memory | 默认/验收测试 | 毫秒级可复现 |
| file | JSON 持久化 | 零依赖演示 |
| sqlite | 真库 | `email UNIQUE` 约束兜底并发抢注 → EMAIL_TAKEN；外键约束；WAL |

**SQL 只存在于实现**：功能永远看不到数据库。SQLite 实现与内存版行为一致（集成测试逐方法对照），
未来平移到 Postgres 只需换实现 + 多 schema（`auth_service.users` 等，方案 B：一个库多个 schema）。

## 11. 人如何负责

1. 验收测试客观：机器判定，无需主观；
2. 验收测试定稿：AI 改验收测试 = CI 红；
3. 权限最小：ticket 只放行 impl.ts；
4. 失败隔离：回滚粒度 = 一个功能；
5. 安全前置：防枚举/防重放/限流/全端下线写死在功能规格里，AI 想漏 = 红灯；
6. 角色分离：生成者 ≠ 验收测试者 ≠ 实现者；
7. **全程留痕**：界面每个确认/编辑/定稿都进 git——"人做了什么"可审计（也救回过未提交代码）。

## 12. 适用边界

| 场景 | 适合？ | 原因 |
|---|---|---|
| 业务服务（CRUD/认证/支付/订单） | ✅ | 边界清晰、验收测试客观 |
| 数据处理管线（ETL） | ⚠️ | 可以，但数据接口换成"输入输出批"，功能粒度更大 |
| 算法密集模块 | ⚠️ | 验收测试可以（黄金测试），功能内耦合多 |
| 探索性原型 | ❌ | 功能规格无法定稿，先自由探索 |
| 强耦合横切改造 | ❌ | 只能走功能规格演进通道 |

判断标准一句话：**"完成"是否可被机器判定？** 能就用，不能先别让 AI 写。

## 13. 语言选型

默认 **TypeScript**：AI 生成质量最高（训练数据量大）+ 类型约束强（编译器是第一道验收测试）+
schema→类型单一来源（zod）+ 验收测试毫秒级（vitest）。

| 情况 | 建议 |
|---|---|
| 默认 | TypeScript |
| 团队全是 Python 且贴近 ML | Python（pydantic + Protocol + pytest，可完整复刻） |
| 基础设施出身、性能敏感 | Go |
| 内存安全级别 | Rust |

红利：数据接口/实现隔离了业务与基础设施，**换语言 = 重写实现与组合根，功能规格原样搬**。

## 14. 实测教训

1. **真实 AI 生成测试校准检查器**：一次抓出初审 2 个假阴性 bug（JSDoc 多行注释误报、不变量计数方式）——mock 练流程，真实产物练检查器；
2. **`git add -A` 双刃剑**：落盘即提交 = 留痕 + 事故保险（未提交代码三次从悬空提交完整找回）；但 `git reset --hard` 会清掉未提交代码——**先提交、再演示、再只回滚演示提交**；
3. **mock 草稿要可编译**：违规 import 注释化展示（评审可见但不破坏 tsc）；
4. **占位验收测试是假绿**：`expect(true)` / TODO 骨架必须补全才可定稿；
5. **新组第一个功能**：一键接入锚点面向 auth-service，新组接入需人工（编译预检会拦住错误接入——失败安全）；
6. **prompt 文件也是代码**：05 曾因 git 事故丢失导致真实模式数据接口生成崩溃——prompt 与代码同仓同版本。
