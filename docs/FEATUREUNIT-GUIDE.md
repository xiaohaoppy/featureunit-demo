> **AI 生成 → 机器判据 → 人确认**，每个产物冻结进 git。

## 1. 缘起

AI 写代码有三个天然问题，框架逐一解决：

| 问题 | 表现 | 解法 |
|---|---|---|
| 判据不客观 | AI"感觉写得对"，没人敢确认 | 判据 = 测试全绿 + 类型检查 + 初审清单，机器判定 |
| 上下文太大 | AI 面对整个代码库容易迷路 | 一次只给 2 个文件（契约 + 实现），其余只读 |
| 人无法负责 | 出问题不知谁的锅 | 契约冻结 + 角色分离 + git 全程留痕，每个决策可追溯 |

## 2. 核心思想

```
人一句话需求 → 系统自动规划（组/端口/单元）
  → 逐步 AI 生成（六 Agent 各司其职）
  → 机器判据把关（初审/红灯考卷/tsc 预演）
  → 人确认 → 冻结（git 提交）
```

**自由与纪律的分界**：单元内自由（AI 怎么写都行），单元间纪律（契约/判据/端口/组合根冻结）。
自由的代价由判据承担，纪律的代价由流程承担。

## 3. 概念分层

| 层次 | 是什么 | 解决什么问题 |
|---|---|---|
| 功能单元 | AI 一次交付的最小单位：contract/spec/impl/test 4 文件 | 上下文极小、判据客观 |
| 端口 Port | 单元与外部世界的唯一切口（纯接口，无实现） | AI 不需要懂 DB/HTTP/日志 |
| 适配器 Adapter | 端口的具体实现（内存/scrypt/sqlite/文件/HTTP） | 换基础设施 = 换一行配置 |
| 服务组 | 一个可部署进程（一个库一个组） | 部署单元，不是微服务 |
| 组合根 | 唯一"知道一切"的文件（index.ts） | 组合逻辑只有一处 |
| manifest | 组清单（版本、规则） | 独立版本、单单元回滚 |

关键区分：**功能单元是开发单元（进程内、可独立测试），服务组是部署单元（一个进程）**。

## 4. 五个机制

1. **判据客观**：测试全绿 + tsc 通过 = 完成，机器判定；
2. **上下文极小**：ticket 只涉及 2 个文件；
3. **失败隔离**：单元独立测试、独立版本（manifest），回滚粒度 = 单单元；
4. **契约冻结**：契约/判据/端口 hash 进 CI，AI 改了判据 = CI 红；冻结守卫（已冻结禁止 AI 覆盖）；
5. **角色分离（test oracle 独立性）**：生成者 ≠ 判据者 ≠ 实现者——B 的判据不是 C 写的，C 必须硬过 B 的考卷。

## 5. 契约体系

### 5.1 六要素模板（`docs/contract-template.md`）

一句话目标 / 输入 / 输出 / 错误码 / 端口 / 不变量。

- **不变量 ≥ 3 条，编号列表书写（1. 2. 3.），条条可被测试断言**（机器初审按编号统计）；
- 用**【不】负责**显式声明非目标；
- 语义中文、签名 TypeScript（zod schema = 可执行规格）。

### 5.2 评审清单（`docs/contract-review-checklist.md`）

10 条，冻结前必过：安全边界 / 错误码齐全 / 端口无泄漏 / 不变量可测 / 【不】负责声明 / schema 够严 / 不写死实现 / 时钟可注入 / 日志禁敏感 / 结果不含敏感。
**AI 负责翻译需求，人负责钉业务风险**（防枚举、防重放、防爆破）。

### 5.3 冻结 = git + 守卫

评审通过 → 文件头写冻结记录（评审人/日期/结果）→ git 提交 → 冻结守卫生效：
已冻结的契约/判据/端口禁止被 AI 生成覆盖（lib + 前端双重拦截）。

### 5.4 契约演进（唯一允许改契约的通道）

1. 新开 v2 契约（旧实现继续跑）；
2. 写迁移测试（v1 数据在 v2 下仍可用，或声明破坏性）；
3. 所有调用方一起升级（人评审）；
4. 删除旧版。整个过程不进 AI 队列。

## 6. 错误处理协议

```
单元只抛 AppError(错误码, 状态码)      ← 业务语义
HTTP 适配器：错误码 → 状态码 + 用户文案   ← 展示层
未知错误：适配器兜底 500 + 服务端日志     ← 不泄漏堆栈
```

- 错误码常量在 `ports/errors.ts`，可 grep、可断言、可枚举；
- 安全相关码有讲究：`INVALID_CREDENTIALS` 同时覆盖"用户不存在"和"密码错误"（防枚举）；
- **错误码一致性检查**（管理台）：spec 声明 vs impl 抛出 vs errors.ts 定义三方核对；
  `INVALID_INPUT` 由组合根 zod 边界兜底，不算单元漏抛。

## 7. 配置与安全

- 优先级：**本地配置文件（`.featureunit.local.json`，git 忽略）→ 环境变量 → 代码默认值**；
- `config.ts` 是唯一读配置的文件（fail fast：缺失即退出）；
- 秘密（AI 密钥等）默认打码，不进功能单元、不进测试、不进日志；
- **AI 配置**：`AI_API_KEY` / `AI_MODEL`（自动从 /models 获取，60s 缓存）/ `AI_REASONING`（low/medium/high）/ `AI_BASE_URL`；
- TTL、限流参数由组合根从配置换算后注入单元。

## 8. 机器判据体系（框架的"考试系统"）

| 环节 | 机器判据 | 语义 |
|---|---|---|
| 端口 | 7 项纪律初审 | 机器查纪律，人查语义 |
| 契约 | 结构/端口引用/tsc 初审 | 考卷质量把关 |
| 判据 | 占位检测（TODO/expect(true) 拒绝冻结） | 考卷没写完不许开考 |
| 实现 | 判据全绿才提交；迭代 ≤5 轮超限停手 | 失败安全：干不了就求援 |
| 打包 | **tsc 预演**（写入→编译→自动还原，零污染） | 编译不过禁止确认 |
| 全局 | 冻结守卫 + 错误码一致性 + 接线检查（6 项缺口） | 多层防线 |

**初审检查器本身也接受"真实 AI 生成测试"校准**——mock 的固定缺陷喂不出的假阴性（JSDoc 多行注释、不变量计数），真实产物一测就暴露。

## 9. 六 Agent 全景

| Agent | Prompt | 产出 | 机器判据 | 流水线推理等级 |
|---|---|---|---|---|
| 需求解析 | `analyzeRequirement` | 组/单元/端口方案 | — | — |
| A 契约设计师 | `01` | contract.ts + spec.md | 结构/端口/tsc 初审 | **high** |
| B 评审员/判据作者 | `02` + `04` | 评审结论 / impl.test.ts | 占位检测 | **high** |
| C 单元实现者 | `03` | impl.ts | 判据全绿才提交 | medium |
| D 端口作者 | `05` | ports/<name>.ts | 7 项纪律初审 | medium |
| E 打包作者 | `06` | 组合根/HTTP/manifest 接线 | tsc 预演 | medium |

**Prompt 质量基线**（已统一）：`{{占位符}}` 风格、输出格式约束（只输出代码块）、
纪律白名单化（禁止 import 什么明确列出）、few-shot 好/坏示例（05）、编号格式约束（01）。

## 10. 数据层与存储

| 存储 | 用途 | 说明 |
|---|---|---|
| memory | 默认/判据 | 毫秒级可复现 |
| file | JSON 持久化 | 零依赖演示 |
| sqlite | 真库 | `email UNIQUE` 约束兜底并发抢注 → EMAIL_TAKEN；外键约束；WAL |

**SQL 只存在于适配器**：单元永远看不到数据库。SQLite 适配器与内存版行为一致（集成测试逐方法对照），
未来平移到 Postgres 只需换适配器 + 多 schema（`auth_service.users` 等，方案 B：一个库多个 schema）。

## 11. 人如何负责

1. 判据客观：机器判定，无需主观；
2. 判据冻结：AI 改判据 = CI 红；
3. 权限最小：ticket 只放行 impl.ts；
4. 失败隔离：回滚粒度 = 一个单元；
5. 安全前置：防枚举/防重放/限流/全端下线写死在契约里，AI 想漏 = 红灯；
6. 角色分离：生成者 ≠ 判据者 ≠ 实现者；
7. **全程留痕**：界面每个确认/编辑/冻结都进 git——"人做了什么"可审计（也救回过未提交代码）。

## 12. 适用边界

| 场景 | 适合？ | 原因 |
|---|---|---|
| 业务服务（CRUD/认证/支付/订单） | ✅ | 边界清晰、判据客观 |
| 数据处理管线（ETL） | ⚠️ | 可以，但端口换成"输入输出批"，单元粒度更大 |
| 算法密集模块 | ⚠️ | 判据可以（黄金测试），单元内耦合多 |
| 探索性原型 | ❌ | 契约无法冻结，先自由探索 |
| 强耦合横切改造 | ❌ | 只能走契约演进通道 |

判断标准一句话：**"完成"是否可被机器判定？** 能就用，不能先别让 AI 写。

## 13. 语言选型

默认 **TypeScript**：AI 生成质量最高（训练数据量大）+ 类型约束强（编译器是第一道判据）+
schema→类型单一来源（zod）+ 判据毫秒级（vitest）。

| 情况 | 建议 |
|---|---|
| 默认 | TypeScript |
| 团队全是 Python 且贴近 ML | Python（pydantic + Protocol + pytest，可完整复刻） |
| 基础设施出身、性能敏感 | Go |
| 内存安全级别 | Rust |

红利：端口/适配器隔离了业务与基础设施，**换语言 = 重写适配器与组合根，契约原样搬**。

## 14. 实测教训

1. **真实 AI 生成测试校准检查器**：一次抓出初审 2 个假阴性 bug（JSDoc 多行注释误报、不变量计数方式）——mock 练流程，真实产物练检查器；
2. **`git add -A` 双刃剑**：落盘即提交 = 留痕 + 事故保险（未提交代码三次从悬空提交完整找回）；但 `git reset --hard` 会清掉未提交代码——**先提交、再演示、再只回滚演示提交**；
3. **mock 草稿要可编译**：违规 import 注释化展示（评审可见但不破坏 tsc）；
4. **占位判据是假绿**：`expect(true)` / TODO 骨架必须补全才可冻结；
5. **新组第一个单元**：一键接线锚点面向 auth-service，新组接线需人工（tsc 预演会拦住错误接线——失败安全）；
6. **prompt 文件也是代码**：05 曾因 git 事故丢失导致真实模式端口生成崩溃——prompt 与代码同仓同版本。
