# FeatureUnit 框架完整指南

> **让 AI 放心写代码的框架**：AI 一次只实现一个小功能（功能单元），
> 很多小功能组合成一个服务组。**人要为 AI 的产品负责**——所以框架的每一层
> 都在回答同一个问题："怎么让 AI 的自由度可控、完成标准客观、错误可追责？"

本指南是对仓库的完整讲解（配套实操见 `TUTORIAL.md`，契约模板见
`contract-template.md`，评审清单见 `contract-review-checklist.md`）。

## 1. 缘起

AI 写代码有三个天然问题，框架逐一解决：

| 问题 | 表现 | 框架的解法 |
|---|---|---|
| **判据不客观** | AI "感觉写得对"，但没人敢确认 | 判据 = 测试全绿 + 类型检查通过，机器判定 |
| **上下文太大** | AI 面对整个代码库，容易迷路、乱改 | 一次只给 2 个文件（契约 + 实现），其余只读 |
| **人无法负责** | 出了问题不知道是谁的锅、改哪里 | 契约冻结 + 角色分离 + 独立版本回滚，每个决策可追溯 |

一句话：**把"AI 敢写"和"服务可靠"这两个目标，拆成"单元内自由、单元间纪律"。**
自由的代价由判据承担，纪律的代价由流程承担，两边都不贵。

## 2. 核心思想

```
契约（人冻结）→ 判据（预先写好）→ AI 只写 impl.ts → 测试全绿 = 完成
```

- **契约是考卷**：定义输入/输出/错误码/不变量，AI 不许改；
- **判据是阅卷机**：`impl.test.ts` 预先写好，AI 的完成标准完全客观；
- **AI 的自由度是受控的**：实现内部想怎么写都行，边界（契约/判据/端口/组合根）绝对不碰。

---

## 3. 概念分层

| 层次 | 是什么 | 解决什么问题 |
|---|---|---|
| **功能单元** Feature Unit | AI 一次交付的最小单位：`contract / spec / impl / impl.test` 4 个文件 | AI 上下文极小、判据客观 |
| **端口** Port | 单元与外部世界的唯一切口（纯接口，无实现） | AI 不需要懂 DB/HTTP/日志 |
| **适配器** Adapter | 端口的具体实现（内存/scrypt/文件/HTTP/SMTP…） | 换基础设施 = 换一行代码 |
| **组合根** Composition Root | 唯一"知道一切"的文件（`index.ts`，人维护） | 组合逻辑只有一处 |
| **服务组** Service Group | 一个可部署进程（本仓库 = 登录系统） | 部署单元，**不是**微服务 |

关键区分：**功能单元是"开发单元"（进程内、可独立测试），服务组是"部署单元"（一个进程）**。
功能单元之间不通过网络通信，避免了微服务的分布式复杂度。

### 3.1 功能单元：4 个文件

```
features/change-email/
  contract.ts      # 契约（冻结区）：zod schema + 接口 + 不变量注释
  spec.md          # 规格（冻结区）：六要素文档（人/AI 可读）
  impl.ts          # 实现（AI 写入区）：唯一允许 AI 修改的文件
  impl.test.ts     # 判据（冻结区）：不变量的机器断言，AI 不许改
```

### 3.2 端口：外部世界的唯一切口

纪律（违反任何一条 = 评审不通过）：

1. 只允许纯数据 + 接口，禁止任何实现代码；
2. 禁止引入 ORM / HTTP / 框架类型（Knex、Prisma、express.Request…）；
3. 语义必须能被内存适配器完整模拟——否则单元无法独立测试；
4. 不可控因素（时钟 `now`、随机数、ID 生成）设计成注入，测试才能固定时间。

### 3.3 组合根：全组唯一的例外

- 功能单元互相不知道对方存在；适配器互相不知道对方存在；
- **只有组合根知道**"N 个单元 + M 组适配器 + 配置"如何拼成一个服务；
- 换数据库、换 Redis、换 SMTP、调 TTL——都只改 `buildDeps()` 里对应的一行。

## 4. 为什么这样设计

### 机制 1：判据客观

```
npm run feat -- test change-email    # 只跑该单元的判据（毫秒级）
npx tsc --noEmit                     # 类型检查（编译器是第一道判据）
```

AI 不需要"感觉写得对不对"——机器说了算。

### 机制 2：上下文极小

一张 ticket 只涉及 2 个文件（只读契约 + 只写 impl）。AI 不会在大代码库里迷路。

### 机制 3：失败隔离

- 单元独立测试、独立版本号（`manifest.json` 记录）；
- 出问题 = 回滚单个单元，其余单元纹丝不动；
- 升级契约 → 新版本 + 迁移测试，坏不了整组。

### 机制 4：契约冻结

- 契约/判据文件的 hash 进 CI：AI 改了判据 = CI 红（机器化反作弊）；
- `manifest.json` 的 `aiWritablePaths` 只放行 `impl.ts`，越界 = 违规。

### 机制 5：角色分离（test oracle 独立性）

```
需求（人一句话）
  → Agent-A：按模板写契约草稿        ← AI 可以干
  → 人（或独立 Agent-B）：评审拍板    ← 必须独立于 A
  → Agent-B：写判据                  ← 不能是 C
  → Agent-C：只写 impl.ts            ← 不能改判据
```

**生成者 ≠ 判据者 ≠ 实现者**。B 的测试不是 C 写的，C 必须硬过 B 的判据——
利益冲突消失，"学生自己出题自己考"不可能发生。

## 5. 契约体系

### 5.1 六要素模板（`docs/contract-template.md`）

一份契约 = 六部分：一句话目标 / 输入 / 输出 / 错误码 / 端口 / 不变量。

- **不变量 ≥ 3 条，条条可被测试断言**（写不出测试的"不变量"是伪要求）；
- 用**【不】负责**显式声明非目标——这是防止 AI 越界写别的代码的关键；
- 语义用中文，签名用 TypeScript（zod schema = 可执行的规格）。

### 5.2 评审清单（`docs/contract-review-checklist.md`）

10 条，冻结前必过：安全边界 / 错误码齐全 / 端口无泄漏 / 不变量可测 /
【不】负责声明 / schema 够严 / 不写死实现 / 时钟可注入 / 日志禁敏感 / 结果不含敏感。

**评审是"人钉业务风险"的环节**：AI 擅长把模糊需求翻译成结构化文档，
但防枚举、防重放、防爆破这类风险必须由人钉进契约。

### 5.3 冻结 = git + CI

评审通过 → 契约头部写冻结记录（评审人/日期/结果）→ git 提交 → CI 对
契约与判据文件做 hash 锁定。任何 agent 提交改动这些文件 → CI 红。

### 5.4 契约演进（唯一允许改契约的通道）

1. **新开版本**：复制 contract.ts → contract.v2.ts，旧实现继续跑（兼容期）；
2. **迁移测试**：证明 v1 数据在 v2 下仍可用（或明确声明破坏性）；
3. **所有调用方一起升级**（唯一的"多文件变更"，走人评审）；
4. **删除旧版**：所有调用方迁完才删；
5. 整个过程**不进 AI ticket 队列**——AI 只认"这是 v2，按 v2 实现"。

## 6. 错误处理协议

```
单元只抛 AppError(错误码, 状态码)        ← 业务语义
HTTP 适配器：错误码 → 状态码 + 用户文案    ← 展示层
未知错误：适配器兜底 500 + 服务端日志      ← 不泄漏堆栈
```

- 单元不产生用户消息（消息只存在于 HTTP 适配器的映射表）；
- 错误码是字符串常量（`ports/errors.ts`），可 grep、可断言、可枚举；
- 安全相关错误码有讲究：`INVALID_CREDENTIALS` 同时覆盖"用户不存在"和"密码错误"
  （防账号枚举）；`INVALID_SESSION` 同时覆盖"无会话/过期/用户已删"（不泄漏细节）。

## 7. 配置与安全

- `config.ts` 是**全组唯一允许读配置**的文件（本地配置 + 环境变量，zod 校验，
  **启动即失败**（fail fast：配置缺失直接退出，绝不带病运行）；
- **优先级：本地配置文件 → 环境变量 → 代码默认值**。本地配置文件是
  `.featureunit.local.json`（**git 已忽略**）——管理台「配置」tab 写的就是它；
- 秘密（DB 密码、SMTP 密钥、AI API Key）不进功能单元、不进测试、不进日志；
  管理台里密钥**默认打码**显示，留空保存 = 删除该项；
- TTL、限流参数等由组合根从配置换算后**注入**单元——单元永远接触不到配置来源。

---

## 8. 观测性

日志也是端口（`ports/logger.ts`）：

- 单元在关键业务节点调用 `deps.logger.info("login.ok", { userId })`；
- 组合根注入真实现（JSON → stdout），测试注入哑实现；
- **PII 纪律是不变量**：密码/token/邮箱不得入日志——写进契约，由判据断言
  （change-email 的判据就有一条"日志不含邮箱"）。

## 9. 发布与回滚

```
groups/auth-service/manifest.json
  # { "register-user": "1.0.0", "login": "1.0.0", ... }
```

- 发布 = 打包整个组 + 记录 manifest；
- **回滚 = 只回滚坏的那个单元**（改 manifest 版本重新部署），其他单元不动；
- 契约版本是兼容性承诺：`1.x` 只加不改，`2.0` 允许破坏性变更（走 5.4 流程）。

---

## 10. 人如何负责

1. **判据客观**：测试全绿 + tsc 通过 = 完成，机器判定；
2. **判据冻结**：契约/判据 hash 进 CI，AI 改判据 = CI 红；
3. **权限最小**：ticket 只放行 `impl.ts` 一个文件；
4. **失败隔离**：回滚粒度 = 一个单元；
5. **安全前置**：防枚举/防重放/限流/全端下线写死在契约里，AI 想漏 = 红灯，
   不是上线后炸；
6. **角色分离**：生成者 ≠ 判据者 ≠ 实现者。

## 11. 适用边界

| 场景 | 适合？ | 原因 |
|---|---|---|
| 业务服务（CRUD、认证、支付、订单） | ✅ | 边界清晰，判据客观 |
| 数据处理管线（ETL） | ⚠️ | 可以，但端口要换成"输入输出批"，单元粒度更大 |
| 算法密集模块（渲染引擎、编译器） | ⚠️ | 判据可以（黄金测试），但单元内状态耦合多 |
| 探索性原型（还不知道要什么） | ❌ | 契约没法冻结，先自由探索 |
| 强耦合横切改造（改数据模型） | ❌ | 只能走正式契约演进通道 |

判断标准一句话：**"完成"是否可被机器判定？** 能，就用；不能，先别让 AI 写。

## 12. 语言选型

默认 **TypeScript**，没有之一。AI 时代的三个决定因素它同时拿高分：

1. **训练数据量**最大 → AI 生成质量最高；
2. **类型约束力**强 → 编译器是第一道判据（AI 在类型层面撒谎 = 编译失败）；
3. **判据速度**毫秒级（vitest）→ AI 的"写→跑→改"循环可以转几十圈。

| 你的情况 | 建议 |
|---|---|
| 默认 | **TypeScript**（zod + vitest + 薄 HTTP 层） |
| 团队全是 Python 人且服务贴近 ML | Python（pydantic + Protocol + pytest，可完整复刻） |
| 基础设施出身、性能敏感 | Go（类型干净，但 schema-first 工具弱一档） |
| 正确性到"内存安全"级别 | Rust（约束最强，但 AI 迭代被借用检查拖慢） |

附赠红利：端口/适配器隔离了业务与基础设施，**语言切换成本也被压低**——
换语言重写的是适配器和组合根，业务语义（契约）可以原样搬。

## 13. AI 工作流全景

```
阶段 0  人/Agent-A 写契约 → Agent-B 独立评审 → 人拍板冻结（git + CI 锁 hash）
阶段 1  写判据 impl.test.ts（人，或独立 AI；禁止实现者写自己的判据）
阶段 2  N 个 ticket 并行发给 AI（互不依赖）：AI 只写 impl.ts，跑到判据全绿
阶段 3  人写/审组合根与适配器；组测试全绿 = 可上线
阶段 4  出问题 → 回滚单个单元（manifest 记录版本）
```

三条固定 prompt（`docs/agent-prompts/`）：

| 文件 | 角色 | 输出 |
|---|---|---|
| `01-contract-drafter.md` | Agent-A 契约设计师 | contract.ts + spec.md 草稿 |
| `02-contract-reviewer.md` | Agent-B 独立评审员 | 10 条清单逐条结论 + 通过/打回 |
| `03-unit-implementer.md` | Agent-C 单元实现者（ticket） | 只写 impl.ts，判据全绿 |

ticket 的纪律条款（Agent-C 必须遵守）：

1. 禁止修改契约/规格/判据/端口/组合根——**测试红了也不许改判据**；
2. 禁止新增依赖；
3. 禁止 import 任何基础设施模块（只允许 `./contract`、`../../ports/**`、Node 内置）；
4. 错误一律抛 `AppError`（错误码见契约第 4 节）；
5. 日志只记业务事实（密码/token/PII 不进日志）；
6. 最多迭代 5 次，超过即停止并报告；
7. 提交信息格式 `feat(<单元名>): implement`，diff 只含 impl.ts。

## 14. AI 生成契约工具

`feat ai-contract`（CLI）与管理台「AI 契约生成」面板（界面）把 Agent-A 变成一条
命令，四步闭环（两者共用 `scripts/ai-contract-lib.mjs`，行为完全一致）：

```
① AI 生成草稿（真实模式调 API / --mock 演示模式）
② 机器初审（结构检查 + 端口引用存在性 + tsc）
③ 人逐条确认（10 项清单 y/n，任一 n = 打回）
④ 全部通过 → 写入冻结记录 + git 提交（冻结）
```

```bash
npm run feat -- new delete-account
npm run feat -- ai-contract delete-account "登录用户可以删除自己的账号（需验证密码）"
# 演示模式：npm run feat -- ai-contract delete-account "..." --mock --yes
```

配置（管理台「配置」tab 或环境变量，优先级：本地配置 → 环境变量 → 默认值）：
`AI_API_KEY`（必填）、`AI_BASE_URL`（默认 https://api.deepseek.com）、
`AI_MODEL`（默认 deepseek-v4-flash；V4 系列——`deepseek-chat`/`deepseek-reasoner`
已于 2026-07-24 停用，迁移只需改这一行）。密钥保存于 `.featureunit.local.json`（不进 git）。

**冻结权永远在人**：EOF（没有明确输入）默认按"打回"处理——没有确认 = 不通过。

## 15. 管理台：界面化管理

`npm run admin` 起管理台（:3001/admin），7 个 tab 覆盖框架全部日常动作：

| tab | 能力 | 对应框架环节 |
|---|---|---|
| 概览 | 单元卡片（🔒 冻结/📄 草稿）+ 运行全部判据 + **端口依赖矩阵**（单元→端口） | 总览 / 总闸 / 审计 |
| 单元详情 | 4 文件查看；运行单单元判据；**在线编辑**（必填说明 + git 留痕）；🔌 **接线检查 + 一键接线**（机器生成组合根/HTTP/manifest 的 unified diff，人确认才落盘）；AI 生成判据 + AI 实现；📜 **提交历史/回滚**（git revert）；⚠️ **错误码一致性检查** | 评审 / 验收 / 人工修改 / 接线 / 回滚 |
| AI 契约生成 | 生成草稿 → 机器初审 → 10 项逐条"通过/打回" → 冻结 | 第 14 章全流程 |
| Ticket | 生成 / 复制任务单 | 发 AI |
| 源码浏览 | 只读查看端口/适配器/组合根/配置（防路径穿越） | 学习 / 审计 |
| 试玩 | 注册/登录/查我/登出/改密/改邮箱/找回密码，cookie 自动流转（内置业务实例） | 冒烟 |
| 配置 | 密钥（打码）与业务参数；来源标注；保存到本地文件 | 第 7 章 |

**多服务组**：`src/groups/` 下每个含 `features/` 的目录即一个服务组，
管理台左侧可切换；lib 全部函数支持 `group` 参数（默认 `auth-service`）。

**错误码一致性检查**：spec 第 4 节声明 vs impl 实际抛出 vs `ports/errors.ts`
定义，三者交叉核对；`INVALID_INPUT` 由组合根 zod 边界兜底，不算单元漏抛。

**界面不替代纪律，只替代操作**：
- 新建单元、AI 生成、冻结、跑判据、出 ticket——界面与 CLI 是同一套逻辑；
- 组合根接线**仍由人写代码**，界面只提供"接线检查"列出缺口；
- 在线编辑任何文件（含冻结区）都允许，但**每次保存强制 git 留痕**；
- 密钥默认打码，写入 `.featureunit.local.json`（git 忽略）。
