# FeatureUnit 上手教程

> 手把手走完"从一句话需求到功能上线"。两条路线：
> **路线 A（推荐）：自动开发**——人只说一句话，系统逐步生成，你逐步确认；
> **路线 B（手动）：分步操作**——理解每个环节后，用管理台/CLI 逐步执行。
> 前置：Node ≥ 20；读完 `USAGE.md`。

## 第 0 步：认识仓库与总闸

```bash
cd featureunit-demo
npm install
npm run check        # 总闸 = tsc + vitest，应全绿
npm run admin        # 管理台 http://localhost:3001/admin
```

关键位置（只记 4 个）：

```
src/groups/auth-service/
  ports/        ← 定稿：外部世界的接口（当前 2 个通用接口：errors/logger）
  adapters/     ← 定稿：适配器（当前只有 HTTP 空壳，业务路由由接入生成）
  features/     ← 每个子目录 = 1 个功能（当前为空框架，等待第一个功能）

scripts/ai-contract-lib.mjs   ← 核心库（CLI 与管理台共用）
docs/agent-prompts/           ← 六条 AI 助手 prompt（01-06）
```

## 第 1 步：路线 A——一句话需求走自动开发

**场景**：需求"支持用户收藏商品"。

### 1.1 开始

管理台 **🏠 开始**页 → 输入 `支持用户收藏商品` → 「开始自动开发」。

系统自动规划（`analyzeRequirement` 关键词解析）：

```
📋 新业务域 → 创建业务系统 favorite-service
📋 需要数据切面 → 生成数据接口 favorite-item
📋 核心动作 → 功能 toggle-favorite
```

### 1.2 逐步确认（每步看产物 + 机器验收测试，再点确认）

| 步 | 你看到的 | 你要做的 |
|---|---|---|
| ① 规划 | 方案 + 理由 | 确认 |
| ② 数据接口 | AI 助手-D 草稿 + 7 项自动检查（⚠️ 缺 JSDoc 等纪律项） | 确认 → 定稿 |
| ③ 功能规格 | AI 助手-A 草稿 + 自动检查（结构/数据接口引用/tsc） | 确认 → 定稿 |
| ④ 验收测试 | AI 助手-B 骨架（N 条不变量 → N 个 it） | **到「功能开发」页补全断言** → 回来确认定稿 |
| ⑤ 实现 | AI 助手-C 迭代轮次（验收测试红→重试→全绿或停手） | 确认（含接受"停手求援"） |
| ⑥ 接入 | AI 助手-E 接入 + **编译预检**（编译不过禁止确认） | 确认落盘 |
| ⑦ 完成 | 🎉 | 总闸 + 冒烟 |

### 1.3 关键体验

- **占位验收测试会被拦截**：第 ④ 步直接确认会报"验收测试仍是占位——请先补全断言"。这是纪律：考卷没写完不许开考；
- **坏接入会被拦截**：第 ⑥ 步如果 编译预检失败，确认按钮不生效（机器验收测试闸门）；
- **mock vs 真实**：没有 API Key 时 mock 模式走完全相同的流程，产物含刻意缺陷（正好练评审）。

## 第 2 步：路线 B——手动分步

想理解每个环节，或自动开发不方便时，手动分步：

### 2.1 建组 / 建功能

```bash
npm run feat -- new-group order-service          # 新组（或面板 ＋）
npm run feat -- new create-order --group order-service
```

生成 4 文件模板：`contract.ts`（功能规格）/ `spec.md`（规格）/ `impl.ts`（实现桩，必红）/ `impl.test.ts`（验收测试占位）。
⚠️ 占位验收测试 `expect(true)` 是"假绿"——验收测试没写之前**不许发给 AI 实现**。

### 2.2 功能规格（AI 助手-A）

```bash
npm run feat -- ai-contract create-order "创建订单" --group order-service --mock
# 真实模式去掉 --mock（需要 AI_API_KEY）
```

流程：生成草稿 → 自动检查（结构/数据接口引用/tsc）→ **你逐条过 10 项评审清单（y/n）** → 定稿（git 提交）。
管理台同款：📦 功能 → ① 功能规格阶段。

### 2.3 验收测试（AI 助手-B）

管理台「AI 生成验收测试」→ 生成骨架（每条不变量一个 it，显式 TODO 必红）→
**人工补全断言**（或管理台编辑文件）→ 「确认验收测试（定稿）」。

> 验收测试质量决定一切：功能规格是考卷，验收测试是阅卷机。补全时覆盖失败路径（错误编号断言）、
> 安全不变量（防枚举/全端下线/PII 不进日志）。

### 2.4 实现（AI 助手-C）

```bash
npm run feat -- ticket create-order    # 打印任务单
# 整段发给 AI，AI 只写 impl.ts → 验收测试全绿才提交
# 或管理台「AI 实现（自动迭代）」：内置迭代器，红→重试≤5 轮
```

**验收测试红不许改验收测试**——纪律红线。

### 2.5 接入（AI 助手-E）

管理台「🤖 AI 接入」→ 生成接入（组合根/HTTP/manifest）→ **编译预检**（自动还原）→ 人确认落盘。
或「🔌 接入检查」看缺口 + diff 预览。

### 2.6 总闸与上线

```bash
npm run check    # tsc + 全部测试
# 冒烟：管理台 🧪 业务测试（空框架为健康检查，接入功能后补充对应操作）
```

## 第 3 步：机器验收测试详解（框架的"考试系统"）

| 环节 | 机器验收测试 | 不过会怎样 |
|---|---|---|
| 数据接口（AI 助手-D） | 7 项纪律自动检查：纯接口/无实现/零 import/无基础设施字样/一句话/Promise/方法带 JSDoc | 检查 ⚠️，人可打回 |
| 功能规格（AI 助手-A） | 结构（schema/编号不变量≥3/spec 章节）+ 数据接口引用存在性 + tsc | 检查 ⚠️，10 项评审拦截 |
| 验收测试（AI 助手-B） | 占位检测（TODO / expect(true) 一律拒绝定稿） | 定稿被拒：先补全 |
| 实现（AI 助手-C） | 验收测试全绿才提交；迭代 ≤5 轮超限停手 | 停手求援（失败安全） |
| 接入（AI 助手-E） | **编译预检**：写入→编译→自动还原 | 编译不过，确认按钮不生效 |
| 全局 | 定稿守卫：已定稿功能规格/验收测试/数据接口禁止被 AI 覆盖 | 报错：走功能规格演进 |

**自动检查器本身也被"真实 AI 生成测试"校准过**：曾抓出 JSDoc 多行注释误报、不变量计数方式两个 bug——mock 的固定缺陷喂不出这种问题。

## 第 4 步：存储模式（框架级配置）

```bash
npm run migrate                       # SQLite 建表（幂等，framework_meta 元数据表）
# 或管理台「配置」→ 存储模式下拉选 sqlite（保存后业务测试面板自动生效）
```

| 存储 | 用途 | 数据在哪 |
|---|---|---|
| `memory` | 默认/验收测试/演示 | 进程内存 |
| `file` | JSON 文件持久化演示 | `data/` 目录 |
| `sqlite` | 真库 | `data/app.db`（migrate 建 `framework_meta` 表） |

**存储模式是框架级开关**：登录/注册业务已移除，当前仅框架元数据使用；
第一个业务功能的数据存储按此接入（内存版 → 换一行配置切真库）。

**存储位置分离**（配置面板可独立控制）：业务数据（`DATA_DIR`/`SQLITE_PATH`）、
业务日志（`LOG_DIR`→`app.log`）、错误记录（`ERROR_LOG_DIR`→`errors.log`）三个位置互不混放——
管理台「配置」tab 底部会实时显示三个位置的目录与现有文件。

## 第 5 步：AI 配置

管理台 **⚙️ 配置** tab：

| 项 | 填什么 |
|---|---|
| `AI_API_KEY` | 你的密钥（打码保存，不进 git） |
| `AI_MODEL` | **下拉自动获取**（或手填 `deepseek-v4-flash` / `deepseek-v4-pro`） |
| `AI_REASONING` | `low`（快省）/ `medium`（默认）/ `high`（深度推理） |
| `AI_BASE_URL` | 默认 `https://api.deepseek.com`，可换任意 OpenAI 兼容端点 |

**推理等级在自动开发中自动分配**：功能规格/验收测试 = high，数据接口/实现/接入 = medium。
`deepseek-chat` 已停用（2026-07-24），迁移只改 AI_MODEL 一行。

## 实战教训（本仓库真实踩过）

1. **验收测试红着不许发 ticket**——占位 `expect(true)` 是假绿；验收测试骨架（TODO）必须先补全再定稿；
2. **AI 草稿必有洞**——评审永远假设它漏了安全边界，逐条过清单；
3. **验收测试会抓实现的语义错误**——"幂等成功 = 不做任何修改（含不清会话）"这类细节，正是验收测试锁行为的意义；
4. **定稿区守卫**：功能规格/验收测试/数据接口定稿后禁止被 AI 覆盖（lib + 前端双重拦截）；
5. **检查器也要被真实数据测试**——真实 AI 生成测试一次抓出自动检查 2 个假阴性 bug；
6. **`git add -A` 是双刃剑**——所有落盘动作强制 git 提交 = 留痕，也是事故保险（未提交代码曾两次从悬空提交完整找回）；但 **`git reset --hard` 会连带清掉未提交代码**——先提交代码、再演示、再只回滚演示提交（本项目踩过三次）；
7. **TS 注释里的 `*/` 陷阱**——块注释中出现 `**/impl.ts` 会提前截断注释（踩过两次）；
8. **mock 草稿要可编译**——违规 import 注释化展示，否则会破坏 tsc 总闸；
9. **配置来源要能看出**——面板标注"本地配置/环境变量/默认值"，改错了一眼定位；
10. **界面操作全部 git 留痕**——你在管理台的每个确认/编辑都可追溯（曾靠它定位"神秘提交"的来源：就是人点的）。
