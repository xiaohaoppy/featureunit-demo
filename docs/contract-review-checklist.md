# 功能规格评审清单：人（或独立评审 AI）对功能规格草稿逐条打勾

> 用途：功能规格草稿（AI 生成的或人写的）必须过这张清单才能定稿。
> 定稿 = git commit + 文件 hash 记入 CI（任何 AI 提交改动规格/测试文件 → CI 红）。
> 为什么需要"人评审"：**人要为 AI 的产品负责**——AI 擅长把需求翻译成结构化文档，
> 但"业务风险"（防枚举、防重放、防爆破）必须由人钉进去。

| # | 评审项 | 检查方法 | 不过怎么办 |
|---|--------|---------|-----------|
| 1 | 安全边界是否覆盖？（防枚举 / 防注入 / 防重放 / 防爆破 / 限流） | 逐条想攻击场景 | 补不变量 + 数据接口 |
| 2 | 每个失败路径都有错误码？ | 对照输入字段和数据接口调用逐个问"失败会怎样" | 补错误码节 |
| 3 | 数据接口里有没有泄漏实现细节（ORM/HTTP/框架类型）？ | 检查数据接口签名与 import | 抽象回去 |
| 4 | 不变量 ≥ 3 条，且每条可被测试断言？ | 逐条写"这条怎么写测试验它" | 改写或删除 |
| 5 | 有没有【不】负责声明？ | 检查第 6 节 | 补上（防 AI 越界写别的） |
| 6 | 输入 schema 够严？（该枚举的枚举、该限长的限长） | 对照 zod 定义 | 收紧 schema |
| 7 | 有没有写死"怎么实现"而不是"做什么"？ | 找"用 X 框架/库"字样 | 删掉，只留语义 |
| 8 | 时钟/随机数/ID 是否可注入？（测试要能固定时间） | 检查 now / generator 是否注入 | 改为注入 |
| 9 | 日志内容是否声明"禁止敏感字段"？ | 检查是否写明（密码/token/PII 不进日志） | 补不变量 |
| 10 | 成功结果是否声明"不含敏感字段"？ | 检查返回类型 | 收紧返回类型 |

## 评审流程（一句话版）

```
草稿 → 逐条打勾 → 全部 ✅ → 定稿（commit + CI 锁 hash）→ 交给验收测试作者写测试 → 交给 AI 写实现
有一条 ❌ → 打回重写（不许带病定稿）
```

## 谁来做评审

- **人**：安全边界（第 1/6 条）和业务拍板（第 4/8 条）必须人点头；
- **独立 AI（AI 助手-B）**：可以做人能形式化检查的部分（第 2/3/5/7/9/10 条），
  但它的结论必须被人复核——**生成者 ≠ 验收测试者 ≠ 实现者**，三条角色线必须分开。
